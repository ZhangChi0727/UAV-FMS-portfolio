## 2. 目标与明确非目标

完成一个可复现的小型闭环：需求记录 → 系统模型元素/关系 → 开发分配或实现定位
→ 验证规定；执行结果/证据作为独立对象，未执行时明确 planned/not_run。
读者能理解一条义务的内容、理由、适用范围、责任和验收方式，并沿关系复核出处。

本轮包含：

1. 标准与建模方法说明、工具能力/限制及裁剪决策。
2. 五条已有 PILOT 记录的结构化字段与关系，保持原义。
3. 一个围绕现有 truth 隔离/控制接口的最小 SysML 2.0 模型切片及必要视图。
4. StrictDoc 与模型之间的单向引用/受控派生、薄层一致性检查和反例。
5. 分层阅读视图、重建说明、实际视觉检查及准确版本的评审包。

不包含：固定“九类图”配额、全仓库 SysML 迁移、完整 MBSE 平台、图形编辑器开发、
模型服务器/API 部署、双向同步引擎、正式需求 ID、全量需求分解、联合冻结、全量证据
平台、跨仓库写入、研究扩展、G2/G3 算法实现或 G0/G1 行为变更。
不修改 G0 冻结配置字节、阈值或审批事实；NAV/CTL/FDI 标识不得重排、复用或删除。
NED/body、SI、scalar-first Hamilton、truth 输入隔离等约定保持不变。

## 3. 标准、方法和工具必须分别说明

### 3.1 规范依据

本轮目标语言标准为 OMG SysML 2.0，不自动追随开发版或工具默认方言。
PA 于本单日期核对官方入口：

- [OMG SysML 2.0](https://www.omg.org/spec/SysML/2.0)：Language 文档标识
  `formal/26-03-02`；TC 应核对所读文档封面、版本和引用章节，不能只引用首页。
- [Language 规范](https://www.omg.org/spec/SysML/2.0/Language/PDF)。
- [官方发布与示例资源](https://github.com/Systems-Modeling/SysML-v2-Release)：
  仅作工具/示例候选入口；使用时固定真实 release/commit，不能用未固定 latest 代替标准。

交付“采用构造—规范章节/页码—工具支持—项目使用—未支持项”表。只需深入核对实际
采用的构造，不以本轮阅读全文或实现全标准为目标。若发布入口发生变化，记录变化；
未经影响分析不自动升级目标版本。引用公开链接与必要定位，不提交规范全文。

区分语言合规、图示记法、工具验证覆盖及项目语义一致性，不能用“解析通过”宣称完整
标准合规。不把 SysML v1 的九类图或 `deriveReqt/refine/satisfy/verify/allocate` 名称
机械套到 v2；针对实际需要逐项核对 v2 构造与方向，项目自定义关系明确标注为扩展。

### 3.2 裁剪后的项目建模方法

记录项目自己的轻量流程：用途/场景 → 需求义务 → 结构与行为分配 → 接口与约束
→ 验证规定 → 变更影响分析。每步说明输入、输出、审查问题、权威源和更新触发条件。
这是一项项目裁剪决定，不声称实施完整 OOSEM、Harmony、Arcadia 或认证流程。
如确实借鉴某方法，补充原始来源、版本、采用部分及未采用部分；不为名词堆叠引入方法。
图或视图只在能回答具体工程问题时建立，列出目的、受众、源元素、更新方式和限制。

### 3.3 工具与依赖控制

StrictDoc 0.30.1 是已有试点起点，先检查其原生 grammar/字段/关系/模板能力。
结构化不能只把 COMMENT 换色，不能用正则表达式自建完整 SysML 解析器。
检测已有 SysML 工具；在具备所需能力的前提下优先最小、可本地重建的文本工具链。
允许按正常权限机制试验一个固定版本的公开工具及所需隔离依赖；记录许可、来源、
版本、运行前提、安装/移除方式和维护成本，不污染 B0/文献虚拟环境或全局设置。
不采购、不创建账户、不部署云服务、不安装新 MCP 前置依赖。
若原生工具无法有界支持需求，提交具体限制与替代方案给 PA；不得悄悄降级标准、
扩大平台建设或将失败检查改成 skip。工具可行性失败可交付决策报告，但本轮不能宣称完成。

## 4. 唯一来源、字段及关系合同

先写字段字典，再改试点：字段名、类型、基数、必需性、枚举、空值含义、来源和校验。
以下为概念要求，不预设未经验证的 StrictDoc 或 SysML 语法：

| 对象 | 最小结构化信息 | 权威边界 |
|---|---|---|
| PILOT 需求/需要/适用性记录 | 临时键、标题、类型、正文、理由、适用性/范围、批准状态、来源定位 | StrictDoc 试点源；不冒充正式需求集 |
| 模型元素 | 稳定试点身份、v2 类型、所属范围、名称、用途及相关约束 | 可编辑 SysML 源；显示名/路径不作为唯一身份 |
| 关系 | 类型、源/目标、方向、依据、是否原生或项目扩展 | 按关系类别明确唯一编辑位置 |
| 开发对象 | 责任组件、planned/implemented 等成熟度；存在时的路径/符号/版本 | 试点映射；不凭链接存在宣称实现完成 |
| 验证规定 | 身份、对象、方法、前提/输入/步骤、独立 oracle、验收条件、阶段 | 独立记录；复用已有批准内容，不发明阈值 |
| 执行/证据引用 | 用例版本、代码/配置版本、命令/环境、结果及证据定位 | 仅引用实际保留证据；未来执行无假链接 |

具体约束：

- 需求正文只有一个权威编辑源。模型如需需求代理，保存引用与必要机器派生内容，
  不手工维护另一份正文；工具需要副本时，单向生成并可检查漂移。
- 模型身份与需求键分离；所有新增试点对象明确非正式，不分配 `B0-REQ-*`。
- 五条原有 PILOT 键不改名，原始正文、理由、适用性决定、验收含义保持。
  一条包含多个义务时记录后续分解建议，不借结构化静默改义务或扩展条目集。
- Parent 只表示已定义的层级，不代表派生、满足、验证等所有关系；既有四个父关系
  保持可追溯。新增有类型关系须说明与旧 Parent 的关系，避免矛盾或重复编辑。
- 支持必要多对多，不强制一需求一组件一测试。验证关系与执行结果独立；批准状态、
  实现状态、执行状态分列。不适用项必须保留范围与真实批准引用。
- 普通 COMMENT 只留非规范性备注；来源、分配、验收、验证与适用性不可继续以混合
  多行散文充当唯一机器数据源。来源集合、关系集合应可逐项识别，不靠显示分隔符猜测。
- G0 参数始终引用固定版本及字段，不再手抄可独立漂移的常量。
- 现有 Markdown 比较夹具可在有限试点中保持等价并自动检查，或改为受控派生；
  写明选择及历史保留方式，不产生第二套正式权威源。

## 5. 顺序执行包（同一 Draft PR，分离提交）

### S1 标准与结构合同

交付简短方法/标准说明、字段字典、关系映射、工具可行性记录和来源归属表。
核对现有模型图，标明哪些仅为说明性图示，哪些构造已核对标准；不整体改名为合规图。
形成拟采用最小切片及工具路径后可继续 S2；若需商业/重型平台、改标准或改义务，先停报 PA。

### S2 五记录结构化与模型切片

迁移五记录的元数据到明确字段/关系，保留迁移前后语义比对。
模型以已有运行时 truth 隔离和控制接口为切片，表达边界、责任主体、必要接口/流向，
以及至少一条需求到模型元素再到验证规定的可双向查询链。开发端对尚未实现控制器
明确 planned，不创建空代码/测试假装完成。可以引用真实现有实现对象，但须解释证据范围。
执行结果对象的字段合同可以定义；不得为了链完整而伪造一次执行或把工具测试当系统验证。

使用官方 v2 语义和可编辑源；调用所选工具实际检查语法、引用与其支持的语义规则。
至少产生一个回答上述工程问题的可读视图，并说明其标准记法/支持边界。
若输出只是项目说明性可视化，应明确标识，不能据此关闭标准图示验收。
不规定图数量；不要为了展示孤立能力增加无用行为/参数模型。

### S3 一致性与展示

建立小型字段/链接校验与单向派生流程，复用原生能力；不建设通用模型数据库。
读者视图默认突出标题、原子义务、适用范围和验收条件；理由、来源、分配、模型、
验证、证据分组。优先原生分组/详情折叠；若不可用，明确次级面板而非长 COMMENT 块。
摘要、模型、详细记录通过身份链接导航；关系方向和状态不只靠颜色表达。
减少冗余侧栏、过多留白与嵌套滚动，长路径可换行，键盘可访问新增交互。
至少在 1280×720 与 1440×900 桌面视口实际检查，记录环境；不扩展为全面移动端适配。
从源生成所有 HTML/图/矩阵；不手改输出，不将 CSS 伪元素作为状态的唯一事实来源。
保留无需工具也能读源的路径，不因追溯工程而损害正文可读性。

### S4 回归、评审与停止

执行下列检查、生成准确 head 的临时预览、更新 PR 与执行 Issue，交 PA 独立复审。
旧 APPROVE 不覆盖本次增量；等待新结论。REWORK 在同一 PR 修正，不另开平行任务。
PA 通过后交用户决定；保持 Draft，除非用户另行明确批准合并。
