## 目标与边界

将已批准的 B0 意图、场景、约束和 G0 合同整理成完整、可分配、可验证的需求与系统模型
联合基线。完整性以 B0 有界姿态实验的用途和范围为边界，不代表完整无人机系统工程。
一级 `systems_engineering/` 同时服务工程决策和读者呈现；轻量化约束维护成本，不降低
模型、开发报告与验证报告的交付地位。

允许：需求源及字段规范、工具试点与决策、模型元素和分配关系、验证规定、风险/假设、
适用性与变更规则、联合冻结清单及审批记录、必要的薄层校验/测试/CI、相关入口更新。

禁止：

- 修改冻结 G0 v1/v2 字节、审批事实、数值阈值或 G1 算法/数值行为。
- 发明、重排或复用 NAV-REQ-*、CTL-REQ-*、FDI-REQ-*；编号批准前分配正式 B0 标识。
- 为匹配当前实现而弱化需求，或把设计选择、代码现状、研究假设都写成系统需求。
- 实施 G2/G3、C 的证据平台/完整追溯自动化、研究扩展、外部验证仓库适配、HIL/飞行。
- 引入大型 MBSE 平台、自建需求数据库、商业账户、新 MCP 前置依赖或重复权威源。
- 提交凭据、版权全文、私有笔记、生成导出或 notebook 输出；删除历史证据或重排模块路径。

若需求整理暴露 G0/G1 冲突，登记冲突、影响和候选处置，暂停该项冻结并请维护者决定；

## 执行阶段二 需求 模型与验证规定

先建立正常运行、初始偏差、阶跃、扰动、噪声、饱和/恢复、非法输入、reset 和复现的
场景覆盖表。每个场景说明用途、环境、输入输出、假设、排除项和相关组件；明确无绝对
yaw 参考、无完整平移动力学等限制，不将有界实验改写为飞行安全承诺。

每条正式需求至少包含：稳定 ID、单一规范性正文、层级/类型、来源定位、理由、适用条件、
分配责任、相关模型元素、验证方法、验收条件、批准状态、变更/替代关系。
顶层需求链接使用目标；派生需求给出依据；无需给所有非功能需求虚构功能父节点。
条件性需求说明激活条件，不用空字段或“待定”掩盖通过标准。

完整性审查至少覆盖：

- Plant、Actuator、IMU、姿态估计、级联控制、集成执行、独立验证的功能分配。
- NED/body、SI、scalar-first Hamilton 四元数、单位/符号、状态所有权与真值隔离。
- 消息有效性、采样/调度、严格配对反馈、场景时钟不回退、epoch-local reset 和输入拒绝。
- 控制器唯一限幅职责、执行器推进配对限幅目标、抗饱和及恢复；不重新定义 G0 语义。
- 数值稳定性、噪声/seed、重置后复现、配置/版本与工具链约束。
- G4 独立指标、有限缺陷检出演示及发布复现，不推迟到研究扩展。

性能值和参数通过冻结配置版本及字段定位引用；需求正文描述义务，不再维护可漂移常量。
CTL-REQ-001/002 当前 B0 的 not_applicable 按
[已追认决定](../../systems_engineering/reports/b0/g0_approval_decision.md)登记，修正当前摘要中
仍称待评审的表述；不改历史正文、不删除旧阈值、不声称已满足。

建立目标→需求→功能/组件→接口/行为→验证规定的必要双向关系。复用 A 的视图标识，
补足元素级引用，区分视图、元素与需求 ID；不把整个文件存在当作关系有效。
模型方向、初始化/正常更新/拒绝/reset、时钟和部署成熟度必须互相一致，并与 G0 对齐。
变更过的图源实际渲染检查，记录版本与受检源，不以语法通过替代语义/可读性审查。

每项验证规定须包含对象/需求、配置与假设、输入及初态、步骤、独立 oracle、指标/单位、
容差与判定、执行阶段、失败处理和预期证据类型。区分 test、analysis、inspection、
demonstration；不仅写“pytest 验证”。G2/G3/G4 规定可以尚未实现，但不能没有验收条件。
已有 G0/G1 测试逐条判断证据充分性，未覆盖义务明确记差距；不得倒签 pass。

将需求批准状态、实现成熟度和验证结果分开。planned/not_run 不意味着需求未定义，
也不意味着满足；不适用项须有范围和批准依据。B 必须具备全量验证规划与可审阅分配，
C 再完成结果状态校验、长期证据索引和完整报告自动化，不得把不可验证的要求先冻结。

## 执行阶段三 联合审查与维护者冻结

进行用途充分性审查和条目质量审查：按场景、功能、接口、异常、工程约束交叉核对，
检查遗漏、重复、冲突、模糊词和不可验证项。条目数量不是完整性的证明。
风险/假设登记须包含影响、依据、责任、处置/验证、关闭条件和剩余限制。

候选冻结包至少包含：

1. 范围和排除项、工具/编号决策、唯一需求源及全部适用性记录。
2. 模型源、元素/分配关系、验证规定及完整性审查矩阵。
3. 风险/假设、差距及非关键待决实现选择，含责任与处理阶段。
4. 联合清单：准确候选源提交、逐文件路径/hash、依赖 G0/G1/A 提交、工具版本及重建命令。
5. 维护者批准请求：说明冻结不等于实现/验证完成，列出新增义务及与既有合同的差异。

冻结门槛：适用需求均有来源、责任和明确验收条件；模型分配可解释；零重复 ID、
零无法解释的断链、零影响范围/接口/通过判定的关键 TBD。非关键实现选择允许延期，
但不能以延期为名回避阈值、场景或责任决定。

先形成候选源提交 S，PA 审阅该版本，再由维护者明确批准 S 与清单中的冻结资产。
之后记录批准事实的提交 A 引用 S；清单不包含自身 hash，不预填未来提交号，明确
批准记录与被批准资产的边界。A 不得改动已批准资产；若改动则重新提交影响与批准。
PA 最终评审包含批准记录的准确 head，不能把此前对 S 的审阅自动当作最终 head 批准。

hash 统一注明 Git blob 字节或明确的规范化方法；工作文件 CRLF/LF 差异单列出处，
不能混用 hash 口径，也不能借规范化隐藏实质变更。冻结后变更记录理由、受影响需求/
模型/组件/验证规定/证据及重验证计划；废弃 ID 保留、不复用。

## 交付 评审与合并门禁

仅在另行派发后，TC 在同一 B PR 中依次提交试点、批准后全面导入、联合审查与冻结记录。
中途停止点不要求拆出额外 PR，也不允许批量创建后续 PR。
PR 交接包含：基点/准确 head、逐项关闭矩阵、工具决策与编号批准、联合清单、维护者
批准定位、实际验证、CI/artifact、base/head 数值比较、双工作区状态和未决项。

PA 对准确 head 给出 APPROVE 或 REWORK；REWORK 必须说明发现、复现/证据和验收要求。
TC 在同一 PR 修复并返回新 SHA；CI 全绿、TC 自评及维护者内容批准都不替代 PA 代码/
文档独立评审。任何 head 变化均须重新取得对应批准，补 PR 证据不必制造无意义新提交。

只有维护者联合冻结批准、最新 head 的 PA APPROVE、全部必需 CI 成功，以及有效用户
合并授权同时具备，才可合并；本单本身不授予合并权。合并前复核远端 head 未变。
合并后返回 merge SHA、双工作区安全同步与回归记录，PA 独立验收。
