## 修复一 抗饱和合同 P1

当前 actual-minus-limited_target 只能反映执行器未达到限幅目标的差值，无法单独
覆盖 request 超限而 actual 已达到 limited_target 的持续饱和。

- 选择并论证完整策略：条件积分、基于未限幅请求的回算，或明确组合策略。
- 写清 request、limited_target、actual 各自生产者、单位、采样时刻、反馈延迟，
  以及积分更新、积分边界、回算系数或条件判定、reset 初值。
- 若保留执行器滞后反馈，说明它与限幅反馈各自的作用；不把两者混淆。
- 配置、校验器、接口账本同步；不要只替换一处字符串而留下相反的硬编码检查。
- 用手算信号例说明 request 超限且 actual=limited_target 时如何阻止继续积累，
  以及未饱和/反向恢复时的行为。仅作合同示例，不实现 PID 或宣称动态性能通过。

验收：后续 G2 能按离散合同实施；校验拒绝不完整策略参数及矛盾的反馈声明。

## 修复二 阶跃语义与观察窗口 P1

- 将跟踪稳定时间从阶跃开始计时，与扰动结束或指令撤回后的恢复时间区分。
- 定义 start/end 是否包含端点、事件结束后保持还是归零、轴角/姿态指令的组合规则。
- 每个阶跃绑定事件标识、参考目标、观察窗口和指标；不得用整段公共窗口掩盖某次失败。
- 窗口须容纳允许稳定时间和驻留检查，并明确截止时仍未稳定的结果表示。
  根据正式定义调整场景时长/间隔，不通过静默放宽性能阈值解决。
- 定义从非零状态到负阶跃的幅值、超调分母与方向，不能只用模糊的“首个幅值”。
- 将未收敛、缺数据、零阶跃不适用分别表示，禁止算成有限稳定时间或性能通过。

验收：逐事件展示 tick 到秒的窗口核算；反例覆盖窗口过短、重叠、乱序及未定义的事件组合。
