## 一级结构与唯一来源

用户已确认一级目录使用 `systems_engineering/`，而非仅设置 `docs/system/` 或以 MBSE
工具名称组织项目。目标结构如下；实施时只创建有实际内容的目录，不交付空占位树。

```text
systems_engineering/
├── README.md       # 系统总览、成熟度说明和读者阅读路径
├── models/         # 系统上下文、功能/架构、接口、行为和部署模型源
├── requirements/   # 唯一需求源、适用性、分配及联合基线清单
├── verification/   # 模块/集成验证计划、覆盖关系和证据索引
└── reports/        # 基线、开发进展、验证与工程评审报告
docs/
├── work_orders/    # 实施步骤与交接工作单
└── ...            # 开发环境、操作指南和日常协作说明
```

系统工程模型回答“系统是什么、为何这样设计、如何构成和交互”；开发报告回答“实现了
哪些分配功能、还有什么缺口”；验证报告回答“哪些结论由哪些证据支持、适用范围是什么”。
原始证据留在既有 artifact/CI 或批准的发布存储位置，报告链接到固定版本和校验信息，
不把所有日志堆入展示目录。RESULTS.md 保持结果摘要入口，链接报告而非复制维护第二套结论。

需求正文只在 requirements 的选定格式维护；模型使用稳定标识引用需求，图示与叙述使用
同一组模型元素/关系。G0 机器合同继续作为既有参数和运行时语义来源，模型引用其版本和
字段，不再手抄一套可独立修改的常量。docs 的操作说明链接模型和报告，不重复维护架构。

默认采用 Markdown、文本化图示（优先试验仓库可直接阅读的 Mermaid）和 Git/PR。
保存可编辑模型源；模型元素标识和必要分配表足以支持追溯，不建设自定义模型数据库。
不强制 SysML、商业建模平台、复杂代码生成或“为满足图种数量而画图”。
需求工具只在试点确有维护收益时采用；若纯文本已满足门槛，可记录理由后由 PA 审阅保留
简化方案，不以安装工具作为系统工程完成标志。

### 最小必要模型与展示验收

A 必须交付真实内容而非空目录。按视角组织模型，可以合并同一张图或同一份源文件：

| 模型视角 | 必须表达的关系 |
|---|---|
| 系统上下文与用途 | 使用者、外部系统、边界、输入输出、B0 使用场景和排除项 |
| 功能与逻辑架构 | 功能到组件分配；Plant/传感器/估计/控制/执行器/集成/验证的责任和依赖 |
| 接口与数据流 | 关键消息流向、truth 边界、单位/坐标、时间语义及数据所有权；引用 G0 字段 |
| 行为与交互 | 初始化、正常更新、非法输入拒绝及运行时 reset 的状态/顺序；不提前实现调度器 |
| 部署与扩展边界 | 当前 Python 组件、计划 C++ 核心及运行环境；B0 与各 EXT 的依赖而非详细设计 |

模型覆盖整个平台的上下文，详细程度以支持 B0 为限。使用清晰图例区分已实现/已验收、
已批准待实现和未激活扩展；不得把计划能力画成已有能力。验证作为独立职责出现在架构中，
不只作为开发组件末尾的测试标注。

每个视图说明用途、范围、适用基线、元素/关系来源和解释入口。保留可编辑源并检查实际
渲染的标签、箭头、图例和阅读顺序；如需预览图，按仓库规则作为可再生成发布资产管理，
不形成第二份模型源。无须建立自动生成全仓库架构的框架。
系统工程 README 提供“用途→模型→需求→实现状态→验证报告→证据”的阅读路线；
面向读者的当前视图从根 README 可达，历史记录保留但不混入当前结论。

## G1.5-B 需求与系统模型联合基线

### 系统定义和需求分类

建立简短 B0 使用场景与系统边界说明，至少覆盖正常运行、初始偏差、阶跃、扰动、
噪声、饱和/恢复、无效输入、reset 和复现。明确使用者、输入输出、运行环境、排除项，
以及无绝对 yaw 参考、无平移动力学等限制。

逐项盘点 charter、development_baseline、architecture、G0 配置与决定、G1 工作单：
区分用户需要、系统/组件需求、设计决定、试验条件、项目任务和研究假设。
不能把现有代码行为反向全部写成需求；当前实现不是需求正确性的唯一来源。
在 A 的模型上建立目标→需求→功能→组件→接口/行为→验证规定的必要关系，允许多对多，
不强制每条非功能需求都虚构功能节点。模型元素标识与需求标识分开，不用目录路径充当
唯一身份。每项适用需求有明确责任；每个 B0 功能有需求来源或经批准的派生理由。

需求覆盖至少包括：

- 有界姿态估计与级联控制的功能及适用场景；性能门槛继承批准合同，不自行发明。
- 物理模型与传感器假设、单位/坐标/四元数约定、真值隔离。
- 接口数据、有效性、采样与调度、时间戳、状态所有权和 reset。
- 数值稳定性、饱和/抗饱和、错误处理、状态不变性及可重复性。
- 配置、软件版本、证据、运行方式和可移植性等工程约束。
- G4 发布复现及有限缺陷检出要求；研究/外部验证套件不作为 B0 前置依赖。

### 标识和字段

先提出 B0 独立编号规则供批准，再分配正式标识；本工作单不创建实际需求 ID。
原有 NAV-REQ-*、CTL-REQ-*、FDI-REQ-* 不改号、不复用、不删除。CTL-REQ-001/002
对当前 B0 不适用的追认决定必须进入适用性表，纠正旧文档仍称待评审的摘要。

每条有效需求至少含：唯一标识、单一明确正文、层级/类型、来源定位、理由、适用条件、
分配组件、验证方法、验收条件、批准状态和变更/替代关系。
父需求可追溯分解，派生需求须说明依据；顶层需求链接使用目标，不能强造父节点。
性能引用须固定配置版本及字段定位，不重复手抄一套可漂移的阈值。
正式需求文本建议使用英文以匹配现有技术资产，评审解释可用中文；两种语言不各自成为权威源。

### 工具试点和选择

先比较当前轻量文本方式的维护成本；StrictDoc 为工具化首选候选，Doorstop 为不适配时
的替代，不要求同时安装两者。先以少量真实代表性条目试点，
覆盖层级、接口约束、性能验收、不适用遗留项和待 G2 实现项，再决定正式采用。
试点在单独工具 venv 内运行，记录固定版本/依赖、许可、安装命令、输出和限制，
不污染现有 `.venv-b0`。不采购服务、不配置付费账户、不安装新 MCP 作为前置条件。

试点必须实测：

1. Git 差异可读；条目标识稳定且能检测重复/断链。
2. 能表示上述字段、分配关系和验证规划，支持人工评审输出。
3. 在当前 Ubuntu/Python 环境和 CI 能以文档化命令生成输出。
4. 输出可带基线版本，工具不可用时仍能读取源文件；有可行迁出路径。
5. 权威需求只维护一次，导出文档/追溯矩阵不作为第二编辑源。

将工具选择、requirements 内的源格式、模型表达方式和编号规则写入简短决策记录，
PA 审阅后再全面导入；需求与模型联合内容由维护者最终批准。若候选增加的维护负担
大于收益，报告具体依据并选择满足门槛的简化格式，不自建需求或 MBSE 平台。
核对所选版本官方文档，不把当前建议视为工具安装已完成：
[StrictDoc](https://strictdoc.readthedocs.io/en/stable/)、
[Doorstop](https://doorstop.readthedocs.io/en/stable/)。

### 需求和模型联合审查与冻结

开展两种审查：需求本身是否足以支撑 B0 预定用途，以及每条需求是否清晰、无冲突、
可分配、可验证。按场景/功能/接口/异常行为交叉检查覆盖，不以条目数量证明完整。
补齐简明风险/假设登记表，含影响、责任、验证/处置和关闭条件，不宣称适航认证。

生成需求到组件、合同、验证用例/计划和已有证据的映射。G0/G1 已有证据标记为既有证据，
逐条审查是否充分；G2/G3/G4 标为 planned/not_run，不创建空测试或假链接充数。
既有证据若不能证明新增提炼的义务，记录差距及受影响任务，不倒签合规。

冻结门槛：

- 范围内每条有效需求均有来源、责任分配、验证方法和明确验收条件。
- 零重复标识、零无法解释的断链、零影响 B0 范围/接口/通过判定的关键 TBD。
- 模型边界、分配、接口方向、状态/时序和部署视图彼此一致，且与 G0 合同一致；
  B0 功能均有依据，模型标注的实现成熟度与 G1 验收及后续计划一致。
- 非关键实现选择可以延后，但列明责任和时点；不得用“以后定阈值”绕过冻结。
- 所有新增义务或与 G0/G1 冲突均经影响分析和批准；不夹带实现修复或静默改参数。
- 维护者确认冻结内容，PA 保存审阅结论、准确提交和未完成实现边界。

联合冻结清单记录需求源、模型源与关系表的版本/hash、依赖的 G0/G1 提交、批准记录及
验证计划版本，不只冻结需求正文。模型渲染方式/工具版本也应可复现。
避免记录文件要求预填自身尚不存在的 commit hash：批准源提交与之后的记录提交分开。
冻结不等于需求已满足；后续更改须记录理由、受影响组件/测试/证据及重验证安排。

|---|---|---|
| 模块验证 | Plant、Actuator、IMU、未来估计器/控制器 | 解析参考、边界/非法输入、性质与独立参考 |
| 接口与集成验证 | 消息配对、采样/时钟/reset、真值隔离、闭环场景 | 合同一致性、运行轨迹、独立指标与场景验收 |
| 系统用途确认 | 在声明的有界姿态实验范围内满足使用目标 | 目标与场景覆盖、局限说明、发布复现与人工审查 |
| 验证有效性 | G4 有限、隔离的符号/单位/抗饱和缺陷注入 | 已批准用例确实检出指定缺陷，不等于证明无缺陷 |

验证计划及覆盖关系统一位于 `systems_engineering/verification/`。
每个验证规定包含：对象/需求/相关模型约束链接、假设、配置、输入、初态、步骤、单位、独立 oracle、
容差/判定、证据位置、执行阶段和失败处理。区分 test/analysis/inspection/demonstration，
人工审查不能伪装成自动测试通过。

追溯应支持需求→分配→用例→结果，以及失败结果→受影响需求。至少区分 planned、
not_run、pass、fail、inconclusive/error 和批准的不适用；工具原生状态不同可提供显式映射。
报告需求验证规划覆盖、已实现测试覆盖、已执行结果覆盖，列明分母；链接存在不等于验证通过。

### 证据与自动化

复用 G1 evidence 和 CI artifact，不改变组件物理实现。定义小型证据清单/索引，记录
代码与配置版本、环境、seed、命令、判定、checksum、生成时间和保留位置。
CI artifact 有保留期；规定发布证据的长期保留与取回方式，过期/缺失不得仍计为可审计通过。
历史无新字段的证据保留原样，标注迁移限制，不重写其数值或生成日期。

在现有 tools 下建立最小治理检查及其独立测试目录，实际路径和命令在 PR 中固定；
不做根目录 pytest 收集。优先使用所选需求工具能力，薄层脚本只补仓库特定校验。
至少检查 ID、必需字段、模型元素引用、需求分配、适用性、验证计划、证据引用以及迁移映射。

检查器本身必须有正反例，至少包括重复标识、缺少验收条件、断裂追溯、证据缺失、
把 planned 错写为 pass、过期或错误版本证据、模型引用未知组件/需求、适用需求未分配。
使用隔离夹具，不篡改真实基线来制造失败。
对 G2/G3 尚未执行的用例，正确的 planned 状态不应导致 CI 失败；假报已验证必须失败。
需求文本质量和数值合理性保留人工审查，不声称 CI 已自动证明。

### 面向读者的工程报告

在 `systems_engineering/reports/` 复用和整理已有内容，提供当前联合基线说明、开发
完成/缺口摘要及验证报告。允许合并成一份清晰报告，不以报告数量验收。每份结论包含
适用范围、实现/配置基点、证据定位、结果和局限；明确区分计划、已实现和已验证。
图示回答系统关系，表格承载准确覆盖和结果，原始数据通过链接下钻；不能只有机器日志。

读者应能从一级入口定位 G1 已验收范围、G2/G3 未实现范围、支持结论的 CI/artifact，
以及需求与模型联合基线。执行两类检查：自动检查链接/基线/关系完整性，人工检查
图示可读性与报告表述是否超出证据。报告发布不能重复维护 Issue 实时执行状态，
使用注明基点的快照并链接 Issue；本增量不要求建设独立网站或新展示应用。

### 扩展边界

EXT-VERIFY 未来负责通用执行/证据接口的适配，RP-VERIFY 负责研究问题和实验设计；
本仓库保留 UAV 语义、场景、指标和缺陷模型。G1.5 只定义接口责任和未来输入输出原则。
未检查外部仓库前不承诺现成兼容、不修改外部仓库、不激活研究包或安排论文数量。
